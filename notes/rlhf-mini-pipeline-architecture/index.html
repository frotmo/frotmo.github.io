RLHF Mini Pipeline
系统架构与核心设计

一个面向入门学习者的、教学级 RLHF 实现：从偏好数据到 PPO 对齐，全部用纯 PyTorch 从零写起。 本文把它拆成可点击的架构图、依赖矩阵、张量级数据流和知识清单 —— 让"RLHF 到底在干什么"变得看得见。

不需要强化学习背景，也不需要 GPU。整个流程在笔记本 CPU 上两分钟内跑完。

01 / Architecture

§1系统架构总览

整个项目按五层组织，自上而下是"谁指挥谁"。最关键的架构决策是： 算法层不依赖模型层——算法只认接口，不认具体实现。点击任意模块查看细节。

⑤ 编排层
SCRIPTS
组装：按顺序调用算法与模型，负责"跑哪一步、存哪个文件"
④ 算法层
ALGORITHMS
通过统一接口调用：generate / completion_log_probs / value（不 import 任何模型类）
③ 模型层
MODELS
读取：把文本变成 id 与张量，把 id 还原成人类可读的回答
② 数据层
DATA
依赖：所有层都从基础层取超参与工具函数
① 基础层
INFRASTRUCTURE
🧩

依赖倒置：算法只认接口

ppo.py、reinforce.py、preference_loss.py、 reward_normalizer.py 一行都不 import 项目内的其它模块，只依赖 torch。 它们通过"鸭子类型"调用 generate() / completion_log_probs() / value()。 换骨干不用改算法，换算法不用改模型。

🏭

工厂模式：一行切换骨干

所有脚本通过 models.build_backbone() 取模型，不直接 new 具体类。 于是 config.arch 从 "transformer" 改成 "lstm" 就能整体换骨干， 其余脚本零改动。

📦

checkpoint 解耦三个阶段

SFT → RM → PPO 通过磁盘上的 .pt 文件串联， 三个阶段可以独立运行、独立调试、独立替换。代价是必须保证 序列形态一致（回答末尾都要追加 <eos>）。

04 / Data Flow

§4数据流向（张量级）

四张"数据流地图"。每一步都标出了张量形状与所在函数—— 照着它就能在代码里对上号。切换标签查看不同阶段。

1
取 SFT 数据
toy_dataset.get_sft_pairs(include_eval=False) → 18 条 (prompt, response) 文本对。
刻意同时混入好回答与坏回答，让 SFT 后 p(正向词) ≈ 0.5 —— 这样 PPO 才有对齐空间。
2
编码并追加 <eos>
tok.encode(response, add_eos=True) → 回答末尾多一个 EOS token，模型才有机会学会"说完就停"。
3
补齐成批
tok.pad_batch() → input_ids [B,T] attention_mask [B,T] loss_mask [B,T]
loss_mask 在 prompt 段为 0、回答段为 1：我们只训练"怎么答"，不训练"怎么背题"。
4
前向
policy(input_ids) → logits [B,T,V]（V = 词表大小 = 36）
5
移位对齐（因果语言模型的约定）
位置 t 的 logits 用来预测 token t+1： logp[:, :-1, :] 对 input_ids[:, 1:]
token_logp = logp[:, :-1, :].gather(-1, input_ids[:, 1:].unsqueeze(-1)) loss = -(token_logp * loss_mask[:, 1:]).sum() / mask.sum()
6
反向传播并保存
Adam(lr=3e-3) × 200 epoch → loss 收敛到 0.1132 （已接近理论下界 ln2/平均长度 ≈ 0.06~0.11）→ checkpoints/sft_policy.pt
1
取偏好对
get_preference_pairs(include_eval=False) → 36 对。 每对含 prompt chosen rejected
9 个训练概念 × 4 条负例（1 条真实负例 + 3 条困难负例：只吐正向词 / 形容词×3 / 概念词×3）。
2
拼成完整序列
encode_pair() = encode(prompt) + encode(response, add_eos=True)
奖励模型看的是"问题 + 回答"整体。序列形态必须与 SFT / PPO 阶段一致，否则会"水土不服"。
3
补齐并打分
c_ids [B,T] c_mask [B,T] → rm(c_ids, c_mask) → r_chosen [B]
r_ids [B,T] r_mask [B,T] → rm(r_ids, r_mask) → r_rejected [B]
4
Bradley-Terry 偏好损失
L = -log σ(r_chosen - r_rejected)
不学"打几分"，只学"这两个里人类更喜欢哪个"。这正是 InstructGPT / Claude 用的同一条损失。
5
验证 + 存最佳权重
每 40 epoch 在 eval 概念的偏好对上算 val_acc / val_loss。
选取规则：准确率优先，准确率并列时取验证损失更低的。 只写 val_acc > best 有个隐蔽 bug —— 本任务 val_acc 第 1 个 epoch 就冲到 1.000 并保持， 于是永远不更新，最终保存的反而是欠训练的第 1 轮权重（chosen/rejected 只差 ±0.9）。
6
保存
→ checkpoints/reward_model.pt（验证准确率 1.000，困难负例被打到 −28.6，与好回答拉开 20 分以上）
PPO 一轮迭代 = 采集（不建图）+ 更新（建图）两段 前 9 步在 @torch.no_grad() 下跑，只算数值；第 10 步才真正建计算图并反传。 梯度只在第 10 步对策略参数求一次。
1
按长度分桶取 prompt
make_prompt_batches() → prompt_ids [B,P]（同批等长，省去 padding）
2
用旧策略采样回答（变长）
policy.generate(prompt_ids, max_new_tokens, eos_id)
sequences [B,P+L] valid_mask [B,L] log_probs [B,L] lengths [B]
遇到 <eos> 逐序列提前停止，所以 L 是"最长的那条"，短序列后面是填充位。
3
重算旧策略的 log π（关键坑）
policy.completion_log_probs(sequences, P) → old_logprobs [B,L]
为什么不直接用 generate 返回的？已结束的序列后面还会继续"采样"出垃圾 token， generate 把它们记成 0；而更新阶段重新前向会得到这些垃圾 token 的真实 log π。 两边不一致 → ratio = exp(new − old) 直接爆 inf。统一重算一次才对齐。
4
参考模型打分
ref_model.completion_log_probs(...) → ref_logprobs [B,L] （参考模型是 SFT 策略的冻结 deepcopy）
5
奖励模型打分
attention_mask [B, P+L] = [1…1 | valid_mask] → reward_model(full_ids, attn) → rewards [B]（原始分）
6
奖励归一化
normalizer(rewards) → normalized_rewards [B] （用跨迭代的 Welford 滑动统计量，再 clip ±5）
rollout.rewards 保留原始分用于上报，rollout.normalized_rewards 才进入训练。
7
奖励塑形：KL 惩罚 + 任务奖励落点
token_rewards = -β · (old_logprobs - ref_logprobs) # 逐 token token_rewards[i, lengths[i]-1] += normalized_rewards[i] # 落在各自最后一个有效位
KL 惩罚是逐 token的，任务奖励是序列级的 —— 只在每条序列自己的结尾加一次。
8
价值估计
policy.value(full_ids)[:, P-1:-1] → values [B,L] （同样按"预测位偏移"对齐）
9
GAE 优势估计（变长特化）
δ_t = r_t + γ·V_{t+1} − V_t A_t = δ_t + γ·λ·A_{t+1} next_value = values[t+1] * mask[t+1] # 技巧 1：序列末尾自动归零 last_gae = (δ + γλ·last_gae) * mask[t] # 技巧 2：填充区垃圾优势不倒流
→ advantages [B,L] returns [B,L]
10
PPO 更新（这一步建图）
优势标准化（之后必须重新乘 mask）→ 打乱 → 切 minibatch → new_logprobs / new_values → ratio = exp(new − old)
surr1 = ratio · A surr2 = clip(ratio, 1−ε, 1+ε) · A loss = −min(surr1, surr2) + vf_coef · (V_new − R)² − ent_coef · H(π) loss = (loss · mask).sum() / mask.sum()
反向传播 → clip_grad_norm_(max_grad_norm=1.0) → Adam(lr=3e-4) 走一步。
1
evaluate.py：对每个 prompt 重复采样
每个 prompt 复制 8 份一次性生成 → full_ids [8n, P+L]。 生成是随机的，只采一次噪声极大 —— 重复采样求平均是 RL 实验的基本功。
2
算三个量
平均奖励（原始分，不归一化，否则跨实验没法比）
平均 KL：KL ≈ E[log π − log π_ref]，只在有效 token 上平均
任务级质量：把全部生成文本交给 task_quality()
3
任务级质量：一把与奖励模型无关的尺子
三个判据只依赖数据集自身定义，完全不经过奖励模型：
· 含正向词：出现 harmful / deceptive / malicious / dangerous 之一
· 概念词正确：出现 prompt 末尾那个概念词（如 worm）
· 成句：长度在 4~7 个 token（没提前闭嘴、也没硬撑到上限）
为什么必须另找尺子？因为"奖励涨了多少"本身会被 reward hacking 污染 —— 策略学会钻空子时，奖励照样涨。
4
ablation_kl.py：配对比较
每个 trial 先 set_seed(42)、从同一个 SFT checkpoint 出发、新建归一化器（统计量不能跨 trial 复用）。
这样曲线上的差异就是 β 的因果效应，而不是随机波动。
5
输出
终端表格 + 两组字符条形图 + ablation_kl_results.md，零第三方依赖（不需要 matplotlib）。

05 / Trade-offs

§5关键设计决策与取舍

每一个"这样写"背后都有一个"所以放弃了那样"。这张表是本项目的核心：动机说明为什么， 牺牲说明代价在哪。

设计选择动机牺牲了什么
默认 Transformer，保留 LSTM 贴近工业界，长程依赖更好；LSTM 作为一行开关的对照实验 参数量约为 LSTM 的 4 倍，CPU 全流程从 ≈1 分钟变 ≈2 分钟
微型 Transformer，而非直接用 GPT-2 完全可读（≈200 行）、零外部依赖、CPU 可训 容量有限，"概念词绑定"仍学不会（但实测证明这是数据问题而非容量问题）
KV cache 增量解码 生成单步从 O(L²) 降到 O(L)，也是工业实现的标准做法 多一份 past_kv 状态要维护；因果掩码必须改用绝对位置比较
pre-LN + 残差缩放 小模型 + 较大学习率下训练更稳 pre-LN 也不是"学习率随便调"：sft_lr 必须从 5e-3 降到 3e-3
空格分词而非 BPE 分词不是 RLHF 重点，避免喧宾夺主 词表无法泛化到新词，OOV 只能落到 <unk>
EOS + 变长生成 让模型学会"何时停"，消除末尾重复，也让 mask 机制真正被用上 引入 padding / masking 复杂度；GAE 终止判断必须按每条序列各自的有效长度处理
奖励读出用 mean 而非 last 堵死"不吐 <eos> 就骗高分"的捷径（Hack ①） 与部分工业实现的 last 约定不同；last 保留为一行开关以便复现该漏洞
偏好数据加"困难负例" 堵死"只吐一个正向词"的捷径（Hack ②） 偏好对从 9 对膨胀到 36 对；数据构造不再"纯净"
KL 写进奖励，而非写进损失 与 InstructGPT / TRL 一致，语义直观："偏离就扣分" 需要正确对齐 value / logprob 的时序（预测位偏移差一位就全错）
奖励用滑动统计量归一化 让奖励尺度与超参解耦，kl_coef 在不同奖励模型之间可移植 训练早期统计量不准，会引入一小段"校准期"；且仍不能跨骨干对齐
优势做 batch 标准化 显著稳定训练，工业界标配 小 batch 时统计量噪声大；标准化后必须重新乘 mask
ppo_epochs = 1 本任务奖励模型只有 36 对数据、比较弱，复用 4 轮会迅速把策略推出安全区 放弃了 PPO 的样本效率优势（奖励模型可靠时调大才是净收益）
价值头复用同一骨干 省一套参数；也说明"奖励模型和 critic 本质是同一种东西" critic 与 policy 共享表征，可能相互干扰
gamma = 1.0 RLHF 的标准做法（不做时间折扣） 不适合有明确回合终止的经典 RL 任务
所有超参集中在 config.py 一处修改、便于复现实验 文件略长
两个刻意的教学设计 ① SFT 数据里同时放好回答和坏回答 —— 让 PPO 有真实的"对齐空间"，否则 SFT 一步到位，PPO 的效果根本看不出来。
② 把三个 reward hacking 完整保留在文档里 —— 它们都是真实调试中撞出来的，比"一次跑通"更能说明 RLHF 难在哪。 相关开关（rm_pooling="last"、include_hard_negatives=False、sft_lr=5e-3）都留着，可以亲手复现每一个。
架构上的一个"非典型"选择 多数教学实现会把"采样 → 算 log π → 算 KL → 算优势 → 更新"写成一个大函数。 本项目把采集（collect_rollout，no_grad）与更新（ppo_update，建图） 拆成两个函数，中间用一个 @dataclass Rollout 传数据。 代价是多写了一个数据类；收益是"哪一步建图、哪一步不建图"变得一目了然， 而且 ablation_kl.py 可以直接复用采集结果做统计。

推荐学习路径

阶段 01 ~ 2 天
先跑起来，再看代码。 按 README 快速开始跑完 train_sft → train_reward_model → train_ppo → evaluate， 观察每一步打印的数字与样例回答。然后读 config.py（所有旋钮）、 utils.py、tokenizer.py（最容易懂的三个文件）， 建立"三阶段流水线"的整体印象。不要一开始就啃 ppo.py。
阶段 13 ~ 5 天
深度学习与语言模型基础（A + B 类）。 重点是 A2 自动微分、A3 交叉熵、B1 自回归约定、B4 因果掩码、B5 残差与 LayerNorm。 配套读 mini_lm.py（40 行，最容易懂的骨干）→ 再读 mini_transformer.py。 读完 B 类你应该能自己写出 completion_logits 的切片。
阶段 23 ~ 5 天
强化学习基础（C 类）。 建议顺序：C1 MDP → C2/C3 策略梯度 → C4 基线 → C7 GAE → C8/C9 裁剪。 配套读 reinforce.py（40 行，只有三行是核心）→ 再读 ppo.py。 看到 ratio = exp(new − old) 时应该能自己解释为什么要 exp。
阶段 32 ~ 3 天
RLHF 专项（D 类）。 重点是 D2 Bradley-Terry、D3 参考模型与 KL、D4 reward hacking（三种具体形态）、D9 评测独立性。 配套读 preference_loss.py → reference_model.py → train_reward_model.py。 这一阶段的核心收获是：奖励模型是代理，代理一定会被钻空子。
阶段 42 ~ 3 天
工程与实验方法（E + F 类）。 重点 E3（采样不可导、必须重算 log π）、E4（mask 的四种用法）、 F2（配对比较）、F3（多次采样降噪）、F6（不要只看单一指标）。 配套跑一次 ablation_kl.py，亲手看一遍"奖励提升高但成句率 0%"的 reward hacking 现场。
阶段 5持续
踩坑清单（G 类）+ 动手扩展。 这 7 条都是本项目真实踩过的坑，每条都对应一次"训练崩掉"。 然后按 §7 的流程做一次扩展（推荐从"新增一个骨干"或"新增一个任务级质量判据"开始）。
07 / Extension Playbook

§7拓展本项目的实践流程

五个最常见的扩展场景，每个都给出可照做的步骤。展开查看，特别注意黄框里的关键细节—— 它们都是踩过坑才总结出来的。

  1. 新建 mini_gru.py，实现一个类，暴露与 MiniTransformer 完全相同的 5 个方法： forward(x)、value(x)、completion_logits(ids, P)、 completion_log_probs(ids, P)、generate(prompt, n, T, eos_id)。
  2. 在 models.py 里把 "gru" 加进 ARCHS， 并在 build_backbone / build_reward_model 里各加一个分支。
  3. 在 config.py 里加这个骨干自己的超参（如 gru_hidden）， 与现有的 embed_dim/d_model 分开，避免语义混淆。
  4. 改 CFG.arch = "gru"，重新依次运行 train_sft.py → train_reward_model.py → train_ppo.py → evaluate.py。
  5. 写一段临时脚本做两个数值自检：增量解码 ≡ 整段前向、因果性（未来 token 的梯度为 0）。 验证通过后删掉临时脚本。
  6. 对照实验：用同一套超参各跑一遍 Transformer / LSTM / 新骨干， 比较 evaluate.py 的任务级质量（不要比奖励绝对值）。
⚠️ 关键细节
  • generate() 必须返回 valid_mask [B,L] 与 lengths [B] —— 整条变长链路（奖励落点、GAE 终止、KL 统计）都依赖它们，缺一个就会静默算错。
  • completion_logits 的切片必须是 [:, P-1 : T-1, :]。 写成 [:, P:, :] 会整体错一位，训练照样跑但永远学不会。
  • value() 只在 with_value_head=True 时存在； SFT / 参考模型 / 奖励模型不需要它。
  • 换骨干必须重跑 SFT 和奖励模型：两个骨干权重结构不同， train_ppo.py 里有一道显式校验（只允许缺 value_head.*）会挡住混用。
  • 如果新骨干是 Transformer 类，记得同时处理 KV cache， 否则生成会退化成 O(L²) 的整段重算。
  1. 新建 dpo.py，只 import torch（保持 ppo.py 那种"算法层零项目内依赖"的风格）。
  2. 算法通过"鸭子类型"使用模型：需要 completion_log_probs() 就调它，不 import 任何模型类。
  3. 新建 train_dpo.py：复用 train_ppo.py 的 make_prompt_batches 与 evaluate_policy，只替换训练循环本体。
  4. 在 config.py 加算法超参（DPO 是 dpo_beta，GRPO 是 group_size）， 与 PPO 的超参分区存放。
  5. 存成独立文件 checkpoints/dpo_policy.pt，不要覆盖 PPO 的结果 （train_reinforce.py 就是这么做的）。
  6. 用 evaluate.py 的任务级质量做三方对照：SFT / PPO / DPO。
⚠️ 关键细节
  • DPO 不需要奖励模型，也不需要参考模型的前向 —— 但需要参考模型的 log π_ref。参考模型仍然要建，只是不参与梯度。
  • DPO 直接在偏好对上训练，所以它天然绕开了 reward hacking； 代价是失去了"在线采样"的能力。
  • 如果新算法需要新的中间量（如 GRPO 的组内相对优势）， 建议同样定义一个 @dataclass 承载它，保持"采集 / 更新"分离的清晰度。
  1. 确定新奖励的落点：是序列级（加在 token_rewards[i, len_i-1]） 还是逐 token（像 KL 惩罚那样直接加在 token_rewards 上）。
  2. 在 ppo.collect_rollout 的奖励塑形段加入新项，注意先归一化再组合， 否则不同量纲的奖励会互相淹没。
  3. 在 toy_dataset.task_quality() 里加一条对应的任务级判据。
  4. 跑 ablation_kl.py 或临时脚本，对比"加了 vs 没加"的质量指标。
⚠️ 关键细节
  • 任何新奖励信号都必须配一把独立的尺子。 否则你无法判断策略是在"真的变好"还是在"钻新空子"。
  • 长度惩罚的经典坑：惩罚"长度"本身会让模型提前闭嘴（输出过短、语义不全）。 更稳的做法是惩罚"超出合理区间的部分"（如 max(0, len − 7)）。
  • 多目标奖励要控制量纲：先各自归一化，再加权求和； 否则权重会变成"哪个奖励数值大就听哪个"。
  1. 把 run_trial 里的 replace(base_cfg, kl_coef=kl_coef) 换成目标参数，例如 replace(base_cfg, ppo_lr=lr)。
  2. 把 --kl 参数改名并调整默认网格（学习率建议扫对数刻度）。
  3. 保留"配对比较"的三要素：同种子、同起点 checkpoint、新建归一化器。
  4. 更彻底的方案：做成通用的 --param name --values ...，用 setattr 动态改配置。
⚠️ 关键细节
  • 评估集只有 3 个 prompt，"奖励提升"这一列的噪声很大； 趋势判断应以 KL 两列 + 任务级质量两列为主。
  • kl_max 这类"最坏值"指标容易被单次尖峰影响，不要作为唯一依据。
  • 扫参时把 --n-samples 调大（默认 32）能显著降低噪声。
  1. 在 toy_dataset.task_quality() 里加一个计数变量与判据， 返回元组多一项（记得同步更新 evaluate.py / ablation_kl.py 的解包）。
  2. 判据必须只依赖数据集自身的定义，不能经过奖励模型。
  3. 在 README 的"实测结果"表里补上这一列，让每次实验都能看到它。
⚠️ 关键细节
  • 本项目已经有一个反例证明这类指标的价值：评估集的"概念词正确率"始终是 0.0%， 而"含正向词率"从 54% 涨到 96%。只看奖励你永远发现不了"偏好学会了、概念绑定没学会"。
  • 判据要"抗钻空子"：例如"成句"用长度区间而不是"长度 > 3"， 否则模型学会"多说几个词"就能骗过它。
08 / What's Different

§8本项目算法 vs 通用方案

RLHF 的实现细节在不同代码库里差异很大。这里逐条列出本项目的做法、工业界的常见做法， 以及为什么这样取舍。有争议的地方都标了说明。

维度本项目做法通用 / 工业做法取舍说明
KL 施加位置 写进奖励（reward shaping），交给 GAE 统一处理 两种都有：trl / InstructGPT 走奖励，部分实现走损失正则项 教学上选奖励更直观："偏离参考模型就扣分"。代价是必须把 value / logprob 的时序对齐到同一个 token 位置。
价值网络 复用策略骨干 + 一个标量头（value_head） 通常用独立 critic 模型 省一套参数、省内存；代价是 critic 与 policy 共享表征可能互相干扰。本项目规模小，收益 > 代价。
奖励读出方式 masked mean pooling（对所有有效位置求平均） 常见做法是取 last token 位置 这是本项目最有价值的一处"反直觉"选择：last 会让"是否以 <eos> 结尾"变成捷径，策略靠"永不吐 EOS"就能把垃圾回答从 −7.92 抬到 +3.33。详见 §9。
奖励归一化 跨迭代滑动统计量（Welford 在线更新）+ clip ±5 部分实现用当前 batch 的均值/方差 batch 统计量会让奖励被"同批次其它样本"影响，信号不可复现。滑动统计量换来的是可复现性，代价是开头有一小段校准期。
变长 GAE 两条显式技巧：next_value = V[t+1]*mask[t+1] 与 last_gae *= mask[t] 多数实现用 padding + mask，但常把终止判断写死成 t == L-1 写死会在变长下出错（短序列的"未来"泄漏成填充位的价值）。显式 mask 化在教学上更清楚。
样本复用 ppo_epochs = 1（同一批数据只复用 1 轮） 通常 4 ~ 10 轮 本项目奖励模型只有 36 对数据、比较弱。实测复用 4 轮（12 次梯度更新）会把策略迅速推离 SFT 分布并触发 reward hacking。奖励模型可靠时，调大才是净收益。
骨干可切换性 工厂 + config.arch 一行开关，两个骨干同接口 通常把骨干写死 这是"为教学服务的架构"：只有能一行切换，才做得起"LSTM vs Transformer"的对照实验。代价是多了一层 models.py 抽象。
评测体系 奖励 + KL + 任务级质量（含正向词 / 概念词 / 成句） 通常只看奖励（或奖励 + KL） 奖励是代理指标，会被 hack；而且不同奖励模型的分数量纲不可比。任务级质量是与奖励模型无关的独立尺子。
偏好数据构造 真实负例 + 程序生成的困难负例（只吐正向词 / ×3 复读） 纯人工比较，不做负例工程 不加困难负例，奖励模型只会学到"有没有正向词"，策略立刻退化成"只输出一个词"。这是用数据解决而非调参解决的典型案例。
依赖与可读性 纯 torch，无 trl / transformers / deepspeed，无 matplotlib 依赖 trl、accelerate、deepspeed 等一整套 换来了"每个文件都能从头读到尾"；代价是无法直接用于真实大模型，需要另做适配层。
09 / Development History

§9完整开发历程

这个项目不是"设计好再写"的，而是一步步撞出来的。按时间顺序记录每一轮改了什么、 为什么改、以及撞到了什么坑 —— 这些坑本身就是最好的教材。

2026-10-09 · 第 0 轮：接手与修复

从"跑不起来的骨架"到可运行的三阶段流水线

接手时项目名为"最简实现"，但实际上跑不起来，也从未真正训练过。逐条排查出五个致命问题：

① train_reward_model.py 用 from data.toy_dataset import ... 的包路径， 但文件其实平铺在根目录 → 直接 ModuleNotFoundError。
② 奖励模型没有训练：只有一次前向 + 打印 loss，没有 .backward()、没有优化器、没有循环。
③ ppo_step.py 数学上是错的：loss = -reward_model(actions).mean() —— 损失里根本没有 log π 项，而 multinomial 采样不可导， 所以 loss.backward() 对策略的梯度恒为零。它连 REINFORCE 都不是。
④ 动作语义混乱：把"位置 × 动作"的混杂张量直接喂给奖励模型当序列。
⑤ 没有参考模型，README 里明写 "Placeholder values"。

修复方式：删除 ppo_step.py，改写为 reinforce.py（教学阶梯②）+ ppo.py（教学阶梯③）； 新增 config.py / utils.py / reference_model.py； 重写 tokenizer.py 为类；把数据集扩到 9 训练概念 + 3 评估概念。

新增 8 个文件 首次跑通 删掉数学错误的 ppo_step.py
2026-10-11 上午 · 第 1 轮：EOS 与变长生成

让模型学会"说完就停"

最初的版本固定生成 6 个 token，于是出现 malware is harmful software software software 这种末尾复读。 根因是模型不知道话已经说完了，只能一直重复到长度上限 —— 这也意味着长度本身不受策略控制。

改动：generate() 维护 finished 布尔向量，逐序列遇到 <eos> 提前停止； completion_mask 从"全 1"变成真实掩码，于是四处必须跟着改： 奖励模型要传 attention_mask、任务奖励要落在各自最后一个有效位、 GAE 终止判断要按各自有效长度、KL 统计只在有效 token 上平均。

这一轮撞到两个坑：① old_logprobs 必须重算（否则 ratio 爆 inf）； ② 优势标准化后必须重新乘 mask（否则填充位优势被平移成非零，出现 inf × 0 = nan）。

变长生成 坑：old_logprobs 需重算 坑：标准化后重乘 mask
2026-10-11 中午 · 第 2 ~ 3 轮：奖励归一化 + KL 消融

让超参变得可移植，并把它测出来

奖励归一化：新增 reward_normalizer.py（Welford 在线均值/方差 + clip ±5）。 关键设计是用跨迭代的滑动统计量，而不是当前 batch 的统计量 —— 后者会让奖励被"同批次其它样本"影响，同一段回答换个批次就换个分，信号不可复现。 归一化只作用于训练，上报指标永远用原始奖励。

KL 消融脚本：新增 ablation_kl.py，一条命令扫完 kl_coef 网格， 自动输出终端表格 + 字符条形图 + Markdown 结果文件，零第三方依赖。 为了公平，每个 trial 做"配对比较"：同种子、同 SFT 起点、新建归一化器。

结果直接产出了一个新默认值：归一化改变了奖励尺度，原来的 kl_coef=0.1 变得偏松， 实测后改为 0.2。同时把 train_ppo.py 的训练循环抽成 run_ppo_training() 等可复用函数，供消融脚本与 REINFORCE 复用。

奖励归一化 消融脚本化 kl_coef: 0.1 → 0.2
2026-10-11 下午 · 第 4 轮：mini-Transformer 骨干

换骨干，然后被三个 reward hacking 教做人

新增 mini_transformer.py（≈200 行 decoder-only Transformer：因果掩码、KV cache 增量解码、pre-LN + 残差缩放）， 配套新增 models.py 工厂实现"骨干与算法解耦"，config.arch 一行切换。LSTM 保留为对照。

数值验证：KV cache 逐步前向 ≡ 整段前向（最大绝对误差 ≈ 1e-7，float32 舍入级）；因果性精确为 0.0。

然后是连续三次崩溃，挖出三个层层嵌套的 reward hacking：

Hack ①「不吐 EOS 就能骗高分」 —— rm_pooling="last" 时奖励模型学到"只在 <eos> 位读分"， 策略只要永不吐 EOS，就能把坏回答从 −7.92 抬到 +3.33。→ 默认改 mean。
Hack ②「只吐一个正向词」 —— 奖励模型给整句 +13.9、给光秃秃一个 dangerous +12.3，后者只要 1 个 token。 策略立刻退化成单字回答，而且加大 KL 惩罚也救不回来。→ 加困难负例后 dangerous 掉到 −28.5。
Hack ③「SFT 没收敛」 —— 最隐蔽的一个，根因根本不在 PPO：sft_lr=5e-3 让 pre-LN Transformer 卡在 loss 0.436（LSTM 同设置能到 0.114）。→ 降到 3e-3 后收敛到 0.1132。

同批还修了一个同类 bug：train_reward_model.py 的最佳 checkpoint 判据只比 val_acc， 而它第 1 个 epoch 就饱和到 1.000，导致保存的是欠训练的权重。 改成"准确率优先、并列时比验证损失"后，chosen/rejected 的分离度从 ±0.9 变成 ±7。

最终结论（也是本轮最大的教学收获）： 奖励的绝对分不能跨骨干比较 —— LSTM 的奖励是 +6.37、Transformer 是 −1.01， 但按与奖励模型无关的"含正向词率"，Transformer 是 95.8%、LSTM 只有 75.0%。

mini-Transformer 骨干解耦 修掉 3 个 reward hacking 95.8% vs 75.0%

10 / Roadmap

§10后续扩展的展望与预期

按"投入产出比"排序。每项都写了预期能看到什么——有明确预期的改动才值得做。

🟢 低成本 · 高收益（建议优先）

📐

评测更充分

增加评估 prompt 数量、每个 prompt 采样更多次，并统计方差。

预期："奖励提升"这一列的噪声显著下降， kl_max 这类最坏值指标不再被单次尖峰主导。

🔁

通用消融框架

把 ablation_kl.py 改造成 --param name --values ... 的通用版。

预期：扫 ppo_lr / clip_eps / gae_lambda 只需改命令行，能快速找到本任务的稳定区间。

🔬

让"概念词绑定"也学会

评估集"概念词正确率"始终是 0.0%，而 Transformer 与 LSTM 都一样 → 这是数据问题。 可引入同一概念的多种句式或做数据增广。

预期：若该指标能从 0% 抬起来， 就验证了"泛化失败源于数据而非容量"这个判断。

🟡 中等成本 · 收益明显

🧮

KL 的两种写法对照

实现"KL 进奖励"与"KL 进损失"两个版本，对比数值差异。

预期：能定量说明两者在什么条件下等价、 在什么条件下会分叉 —— 这是工业实现里最常见的分歧点。

⚖️

长度惩罚 / 多目标奖励

加长度惩罚，或组合多个奖励信号，演示如何缓解 reward hacking。

预期：消融里 β 很小时"长度顶到上限"的现象消失； 但要小心新的 hacking —— 惩罚过重会让模型提前闭嘴。

🪜

"教学版 PPO"：序列级奖励 + 折扣 1

做一个简化版，让读者先在更简单的设定下理解裁剪，再进入 token 级 MDP。

预期：把"token 级 MDP"这个最劝退的概念 拆成两步走，学习曲线明显变缓。

🔴 高成本 · 更接近工业界

🤗

接入 HuggingFace GPT-2

把同一套 ppo.py 套到真实预训练模型上，并与 trl 的结果做对照。

预期：由于本项目已做到"骨干可替换"， 这一步主要只需补一个适配 GPT2LMHeadModel 的骨干包装类 —— 这本身就是对架构解耦程度的一次检验。

🎯

DPO 对照实现

同一份偏好数据，分别跑 PPO 和 DPO（Direct Preference Optimization）。

预期：DPO 绕开了奖励模型与强化学习， 天然免疫 reward hacking，但失去在线采样的能力。对比两者非常有启发性。

🚀

分布式 / 显存优化

LoRA 微调、梯度检查点、8-bit 优化器等工程实践。

预期：把教学实现与生产实现之间的 "最后一公里"补齐 —— 但这部分会显著增加代码复杂度， 与"完全可读"的目标冲突，需要权衡是否放进主分支。

一句话总结这个项目教会我们的事 RLHF 的难点不在"把 PPO 写出来"——那是 200 行的事。真正的难点是： 奖励模型只是一个代理，而任何代理都会被钻空子。 本项目用三个真实的 reward hacking 案例（不吐 EOS / 只吐一个词 / SFT 没收敛） 证明了这一点，并给出了三条对策：改数据（困难负例）、 改读出方式（mean pooling）、配一把独立的尺子（任务级质量）。
