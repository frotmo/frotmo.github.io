分布式系统，到底在解决什么问题？

一句话：让一群会随时坏掉的普通计算机，合作起来像一台永不宕机、又快又能装下一切的"超级计算机"。 听起来简单，但"会坏掉"和"网络不可靠"这两件事，让一切都变得极其困难。

主题一

容错 Fault Tolerance

1000 台机器、庞大的网络，故障是常态而非例外。核心思路是复制：同一份数据存多份，坏了一台用另一台。 但"复制"立刻带来下一个难题——怎么保证多份副本一模一样？

主题二

一致性 Consistency

基础设施必须有明确的行为约定，比如"读到的必须是最近一次写入的值"。这就是线性一致性。 问题是：一致性、可用性、性能三者常常互相冲突，你必须做取舍。

主题三

性能 Performance

目标是可扩展的吞吐量：N 台机器带来 N 倍性能。手段是分片（sharding）——把数据切开分散到多台机器并行处理。 但分片又会和事务、一致性打架。

🔑

贯穿全课的核心张力：容错和一致性都需要"通信"（把数据发给备份、确认缓存是否最新）， 而通信又慢又难扩展。所以真实系统里，设计者常常牺牲一致性来换速度—— 这就是为什么你会看到 GFS 的"弱一致性"、Memcached 的"最终一致"、Bitcoin 的"最长链胜出"等各种各样的设计点。

新手答疑

开始之前，你可能想问

只要初步的操作系统知识就够了：知道进程、线程、内存、文件是什么，听说过"锁"和"并发"。 编程方面，会任意一门语言即可——Lab 用 Go，但 Go 很好上手，本站的 Lab 手册里专门有一节讲 Go 的并发范式。 不需要任何分布式系统基础。

不必。课程本身也只要求每讲前读一篇。对初学者，建议优先吃透这几篇"主干"： MapReduce → GFS → Paxos → Raft → 线性一致性 → Spanner。 它们串起了"并行计算 → 分布式存储 → 共识 → 一致性 → 全球事务"的完整主线。 其余论文可以当作"设计取舍的对照组"来读，理解它们各自解决了主干方案的哪个痛点。

Lab 的难度是真实的（课程自己也标了 moderate/hard）。但难的不是算法，而是并发调试。 建议：① 先看 Lab 手册的"设计目的"和"必备原理"，建立整体框架再写代码； ② 每写一小块就跑一次测试，别攒着；③ 全程开 -race； ④ 卡住时回到对应论文，Lab 文档简略的地方，论文里往往有完整逻辑。

课程近年把 MapReduce 论文里的 "master" 改称 coordinator（协调者），避免与历史上有争议的术语混淆。 两者指的是同一个东西：负责分发任务、跟踪进度的那个中心进程。
