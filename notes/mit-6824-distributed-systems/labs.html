通用前置：五个 Lab 都会用到的分布式原理

在写任何代码之前，先把这几个概念装进脑子里。它们会在每个 Lab 里反复出现。

RPC 让"调用另一台机器上的函数"看起来像本地调用。但它和本地调用有一个本质区别：你无法区分下面几种失败——

  • 请求根本没送到服务器；
  • 服务器执行了，但在回复前崩了；
  • 服务器执行并回复了，但回复在网络上丢了。

客户端只能观察到"没收到回复"。这个不确定性是所有分布式难题的根源。Go 的 RPC 库是"至多一次"语义： 它绝不自动重发请求，收不到回复就返回错误。

Go RPC 调用的标准写法（Lab 1/2/4 通用）
args := &PutArgs{Key: "x", Value: "1", Version: 0}
reply := PutReply{}                 // 必须传"零值"的 reply！
ok := ck.clnt.Call("KVServer.Put", args, &reply)
if !ok {                            // false = 没收到回复（不是"服务器返回了错误"）
    // 需要自己决定：重试？还是放弃？
}
// 注意：Go RPC 只序列化首字母大写的字段，子结构也必须大写

关键陷阱：调用前不要把 reply 的字段设成非零值，否则 RPC 库可能静默返回错误结果。每次调用都要用新的零值 reply。

如果多个副本从相同的初始状态出发，执行相同顺序的、确定性的操作，那么它们最终会到达相同的状态。 这就是复制状态机（Replicated State Machine）。

于是"让副本保持一致"这个问题，被转化成了"让副本对操作顺序达成一致"——而后者正是共识协议（Raft）要解决的。 这是整个 Lab 3→4→5 的设计主线：Raft 负责定序，应用层负责执行。

🔑

这就是为什么 Raft 要维护一条"日志"：日志就是"操作顺序"的载体。领导者把操作追加到日志并复制给多数派，一旦提交，所有副本按同样顺序执行。

任意两个"多数派"必然相交，这是所有共识协议的数学基石。3 台机器中任意两个"2 台"的组合必然有交集； 5 台中任意两个"3 台"也必然有交集。这个交集保证了：上一轮被多数派认可的信息，下一轮一定有人记得。

推论：2f+1 台机器可以容忍 f 台故障。3 台容忍 1 台，5 台容忍 2 台。另外，"多数派"是相对于全部服务器计算的，不是相对于"活着的服务器"。

MapReduce 的重跑、Raft 的日志重放、客户端 RPC 的重传——都会导致"同一个操作被执行多次"。 如果操作不是幂等的，多次执行就会出错。

两类处理方式：① 让操作本身幂等（比如 Map/Reduce 是纯函数，重跑结果一样）； ② 用唯一标识去重（服务器记住"这个请求我已经处理过了"，重复请求直接返回上次的结果）。Lab 2 的版本号、Lab 4 的请求 ID 都是后者。

你无法直接知道"对方死了"，只能通过"一段时间没收到消息"来猜测对方死了。 这就带来一对矛盾：超时太短会误判（把慢当成死），太长则恢复迟钝。Lab 1 要求 10 秒，Lab 3 要求选举超时在合理范围内。

重要认知："故障检测器"永远可能出错，但分布式系统依然工作，因为所有节点都服从同一个（可能出错的）判断。 一致性比"判断正确"更重要——这是避免脑裂的关键哲学。

通用前置：Go 开发范式（Lab 必备）

Go 上手很快，但它的并发模型需要一点思维转变。下面这些是五个 Lab 里你一定会用到的模式。

1. goroutine：把"等待"变成并发

在函数调用前加一个 go，它就在一个新线程（goroutine）里异步执行。Lab 里到处都需要它： 服务器要同时处理多个请求、Raft 要同时发心跳和收消息、MapReduce 要并行跑任务。

goroutine 与竞态
// 顺序执行：慢，一次只能做一件事
fetch(url1); fetch(url2)

// 并发执行：快，但要小心共享数据
go fetch(url1)
go fetch(url2)

// 危险：两个 goroutine 同时改 n，结果不确定 —— 这叫"竞态(race)"
// 必须用锁保护，或避免共享可变数据
🛡️

救命工具：永远用 go test -race 跑测试。它能检测出"结果碰巧正确、但存在竞态"的代码。Lab 里 90% 的诡异 bug 都靠它定位。

2. sync.Mutex：保护共享状态

Raft 的状态、KV 服务器的表、MapReduce 协调者的任务表，都是被多个 goroutine 共享的。任何一次读写都必须持锁。

锁的正确用法（Lab 3 Raft 的核心模式）
type Raft struct {
    mu        sync.Mutex    // 保护所有共享字段
    currentTerm int
    votedFor    int
    log         []LogEntry
}

func (rf *Raft) GetState() (int, bool) {
    rf.mu.Lock()
    defer rf.mu.Unlock()     // defer 保证一定解锁，即使中途 return
    return rf.currentTerm, rf.state == Leader
}

// 铁律：不要在持锁时做耗时操作（如 RPC、磁盘 IO）
//      也不要持锁时向 channel 发送（可能阻塞）
//      正确做法：持锁时把需要的数据拷出来，解锁后再做耗时操作

3. sync.Cond：等待某个条件成立

Lab 1 的"reduce 要等所有 map 完成"、Lab 4 的"提交要等日志被应用"，都需要"等待条件成立"。 time.Sleep 轮询虽然能work但很浪费，sync.Cond 才是正解。

条件变量（Lab 1 / Lab 4 通用）
cond := sync.NewCond(&mu)

// 等待方：必须用 for 循环包裹 Wait()，防止虚假唤醒
mu.Lock()
for !conditionMet() {
    cond.Wait()      // 内部会释放锁并阻塞，被唤醒后重新加锁
}
mu.Unlock()

// 通知方：改变了条件后，唤醒等待者
mu.Lock()
changeState()
cond.Broadcast()     // 或 cond.Signal() 唤醒一个
mu.Unlock()

4. channel：在 goroutine 之间传递数据

Lab 3 的 applyCh、Lab 4 的提交结果传递，都用 channel。channel 同时完成"传值"和"同步"： 发送方会阻塞直到接收方收到。

channel 的两种用法
ch := make(chan int)        // 无缓冲：发送方阻塞直到有人接收
ch := make(chan int, 10)    // 有缓冲：缓冲区满之前不阻塞

go func() { ch <- 42 }()     // 发送
v := <-ch                    // 接收（会阻塞直到有值）

close(ch)                    // 关闭后，range 会自然结束
for v := range ch { ... }
🧭

何时用锁、何时用 channel？课程建议：对于共享状态，优先用 sync.Mutex/sync.Cond； 对于"传递所有权/通知事件"，用 channel。Raft 这种有大量共享状态的结构，用锁更自然。

5. 定时器：不要用 time.Timer/Ticker

Lab 3 的说明里特别强调：用 time.Sleep 的循环来实现周期性动作，别用 time.Timer/time.Ticker——后者在并发场景下极难用对。

Raft 的 ticker 模式
func (rf *Raft) ticker() {
    for !rf.killed() {
        // 检查是否该发起选举（用随机超时避免选票分裂）
        rf.mu.Lock()
        if time.Now().After(rf.electionDeadline) {
            rf.startElection()
        }
        rf.mu.Unlock()
        time.Sleep(10 * time.Millisecond)   // 别空转！
    }
}

Lab 1 · MapReduce moderate/hard

这是唯一一个"从零搭建并行框架"的 Lab，也是理解"分布式系统如何隐藏复杂性"的最好入口。

设计目的

亲手实现 MapReduce 论文里的架构：一个 coordinator（论文中叫 master）负责分发任务， 多个 worker 并行执行 Map/Reduce，通过 RPC 通信。你会亲自体会到三件事： ① 并行任务如何切分与调度；② 如何在"worker 会崩溃"的前提下保证结果正确；③ 为什么 Map/Reduce 必须是确定性纯函数。

必备原理
  • 任务与分片：每个输入文件对应一个 Map 任务；中间键按 hash(key) % nReduce 分成 nReduce 个桶，对应 nReduce 个 Reduce 任务。
  • Shuffle（洗牌）：Reduce 任务要从每一个 Map 任务那里拉取属于自己桶的中间数据。这是全流程最耗网络的一步。
  • 容错 = 重跑 + 原子提交：coordinator 超时（本 Lab 用 10 秒）后认为 worker 已死，把任务重新派给别的 worker。为防止读者看到写了一半的文件，必须"写临时文件 → 原子重命名"。
  • 心跳与任务状态：coordinator 需维护每个任务的状态（未开始/进行中/已完成），并用时间戳判断是否超时。

原子重命名：论文 §3.4 明确提到这个技巧——"当 Reduce 任务完成时，它把临时文件原子地重命名为最终输出文件"。这正是 Lab 里 os.Rename 的出处，用来防止崩溃时留下半成品。

备份任务（Backup Tasks）：论文 §3.6 讨论了"掉队者（straggler）"问题——某台机器因为磁盘/网络问题特别慢，会拖垮整个作业。 解法是对最后几个未完成的任务启动备份执行，谁先完成用谁的结果。Lab 文档提到："如果实现备份任务，注意只有在等待足够长时间（如 10 秒）后才能启动，否则会调度多余任务。"

确定性要求：论文 §3.1 强调 Map/Reduce 必须是确定性的纯函数，否则"重跑"会导致不同 Reduce 看到同一个 Map 的不同输出。

新手提示
  • 中间文件名建议用 mr-X-Y（X = Map 任务号，Y = Reduce 桶号），Reduce 任务读取时遍历所有 X。
  • 中间数据用 encoding/json 存取即可，论文没有规定格式。
  • coordinator 是并发的 RPC 服务器，所有共享状态都要加锁。
  • worker 退出的一种简单办法：如果 call() 返回 false，就假定 coordinator 已退出（任务全部完成），自己也退出。
  • 用 mrapps/crash.go 插件来测试崩溃恢复。

Lab 2 · Key/Value Server easy → moderate

Lab 2 是"最容易被低估"的一个：代码量不大，但它是理解线性一致性和"至多一次语义"的最佳场所。

设计目的

构建一个单机 KV 服务器，但要在网络会丢包的前提下，保证每个 Put 操作至多执行一次， 并且整体行为是线性一致的。然后用这个 KV 服务器实现一个分布式锁。它为 Lab 4（用 Raft 复制这个服务器）打基础。

必备原理
  • 版本号与条件写：Put(key, value, version) 只有当传入的 version 等于服务器当前版本时才成功，并让版本加一。 version=0 表示"创建新键"。这是"比较并交换（CAS）"思想的体现。
  • 至多一次语义（at-most-once）：网络可能丢请求，也可能丢回复。客户端必须重试，但重试可能导致服务器收到重复请求。 对 Put 而言，因为它是"条件写"，重复的 Put 会被版本号挡掉（返回 ErrVersion）。
  • ErrMaybe 的微妙之处：如果客户端重传后收到 ErrVersion，它无法确定到底是"自己第一次的 Put 已经成功、只是回复丢了"， 还是"别人先改了、自己两次都没执行"。所以此时必须返回 ErrMaybe（"可能执行了，也可能没有"），由上层处理。

线性一致性定义：见 Linearizability 论文。Lab 的目标就是让 Clerk.Get/Put 从客户端视角看是线性一致的。

重复请求问题：线性一致性论文里的"例 6"正好说明了为什么"网络重传导致同一请求执行两次"会破坏线性一致性——这正是 Lab 要求 Put 至多一次的原因。

版本号方案：这个"用版本号做条件写"的做法，与 ZooKeeper 的 setData(path, data, version) 完全一致，也是 Chain Replication 论文里提到的"给 put 加版本号"的重复检测方案。

新手提示
  • 实现锁时，需要为每个锁客户端生成唯一 ID：kvtest.RandValue(8)。
  • 重试之间要 time.Sleep(100 * time.Millisecond)，别死循环猛发。
  • 服务器端不需要为了不可靠网络做任何修改——一切重试都在客户端。

Lab 3 · Raft hard

全课程最核心、也最难的 Lab。它分四部分，必须按顺序完成——后面的部分依赖前面的正确性。

设计目的

实现 Raft 共识协议，作为可复用的模块，供后续 Lab 构建容错的 KV 服务。 它要让一群机器"看起来像一台机器"：客户端请求被排成一个序列（日志），所有副本看到相同的日志、以相同顺序执行。

必备原理（按部分拆解）

目标：选出唯一的领导者，并在无故障时保持、在领导者故障时重新选出。

  • 任期（Term）：逻辑时钟，每选举一次递增。一个任期至多一个领导者。
  • 选举机制：节点在"选举超时"内没收到领导者心跳，就自增任期、转为候选者、给自己投票并向所有人拉票；获得多数派即当选。
  • 随机化超时：给每个节点的超时加随机抖动，避免选票分裂。论文建议 150–300ms，但本 Lab 因心跳频率限制（每秒最多 10 次），需要更大的超时。
  • 心跳：领导者周期性发送空的 AppendEntries 来宣示主权、压制新选举。
⚠️

测试要求：领导者每秒心跳不超过 10 次；旧领导者故障后5 秒内必须选出新领导者。这两个约束共同决定了你的超时取值范围。

目标：领导者能追加新日志并复制到多数派，从而提交。

  • 索引从 0 开始：建议在 index=0 放一个 dummy 条目（term=0），这样第一条 AppendEntries 的 PrevLogIndex 可以是 0，永远合法。
  • 一致性检查：AppendEntries 携带 PrevLogIndex 和 PrevLogTerm，追随者只有匹配才接受。
  • 提交规则：领导者只有在当前任期的条目被复制到多数派后，才能推进 commitIndex（这是 Figure 8 的教训）。
  • 选举限制：只有"日志至少一样新"的候选者才能获得投票——保证新领导者拥有所有已提交条目。
  • 性能：循环里要加 sleep 或条件变量，不能空转，否则会因超时失败。

目标：服务器重启后能恢复状态，继续服务。

  • 需要持久化的状态（Figure 2）：log[]、currentTerm、votedFor。
  • 为什么是这三样？log 防止已提交条目丢失；votedFor 防止同一任期投两次票；currentTerm 防止跟随过期的领导者。
  • 不必持久化：commitIndex、lastApplied、nextIndex[]——它们是易失的，重启后重新推导即可。
  • 快速回退优化：Figure 2 的"一次退一条"太慢。论文 §5.3 末尾给出方案：拒绝消息里带上 XTerm/XIndex/XLen，领导者据此一次跳过整个冲突任期。

目标：让日志不会无限增长，并支持把快照发给落后太多的追随者。

  • 快照：服务层周期性调用 Snapshot(index, data)，Raft 丢弃 index 之前的日志。
  • InstallSnapshot RPC：当领导者需要的日志已被丢弃时，改为发送整个快照（本 Lab 要求一次发完，不实现分片 offset 机制）。
  • 持久化快照：用 persister.Save(state, snapshot) 的第二个参数保存快照；重启时要 ReadSnapshot() 恢复。
  • 内存回收：丢弃日志时要确保没有指针指向旧条目，否则 Go 的 GC 无法回收内存。

Lab 4 · Fault-tolerant Key/Value Service hard

把 Lab 2 的 KV 服务器和 Lab 3 的 Raft 组合起来，得到一个容错的、线性一致的KV 服务。分三部分。

设计目的

实现一个"复制状态机（RSM）"包 rsm，它夹在服务层和 Raft 之间： 服务层调用 rsm.Submit(op)，rsm 内部调用 raft.Start() 并等待结果； Raft 提交后通过 applyCh 通知 rsm，rsm 把操作交给服务层的 DoOp() 执行，再把结果返回给最初调用的 goroutine。 这个 rsm 会被 Lab 5 复用。

必备原理

核心是匹配"提交的操作"与"等待的 Submit 调用"：Submit 给每个操作包一个唯一 ID，reader goroutine 收到 applyCh 消息后，用 ID 找到对应的等待者，把 DoOp() 的结果交给它。

  • 关键难点：领导者中途失去领导权。Submit 调用了 Start()，但操作还没提交时领导者就下台了——这个操作永远不会有结果。
  • 检测方法：观察 Raft 的任期是否改变，或 Start() 返回的 index 处出现了别的操作。检测到就返回 ErrWrongLeader。
  • 如果旧领导者被单独分区，它永远不知道新领导者存在——但同一个分区里的客户端也连不上新领导者，所以"无限等待"是可以接受的。

用 rsm 复制一个 KV 服务器：客户端把 Put/Get 发给当前领导者对应的 kvserver，服务器通过 rsm.Submit 把操作写入 Raft 日志，各副本在 DoOp 里执行。

  • Get 也要走日志：如果服务器不在多数派中，就不能回复 Get（否则可能返回过期数据）。最简单正确的做法是让每个 Get 也经过 Submit（不做论文 §8 的只读优化）。
  • 客户端重试：客户端不知道谁是领导者，发错了就换一台重试。建议客户端记住上次成功的服务器，下次优先发给它。
  • 至多一次：同一个 Put 可能被重传多次，必须保证只执行一次（复用 Lab 2 的思路）。

让 KV 服务器周期性调用 Raft 的 Snapshot()，以限制持久化 Raft 状态的大小。

  • 触发条件：比较 rf.PersistBytes() 与 maxraftstate（测试器传入）。maxraftstate = -1 表示不需要快照。
  • 快照内容：不只是 KV 表，还要包含"用于去重的客户端请求记录"——否则重启后可能重复执行请求。
  • 重启恢复：rsm 重启时用 persister.ReadSnapshot() 读取快照，若非空则调用 StateMachine.Restore()。
  • 注意：快照里所有结构体字段必须首字母大写。

Lab 5 · Sharded Key/Value Service hard

全课程的收尾大 Lab，也是"把前面所有东西拼成一个真实分布式系统"的一步。

设计目的

把数据分片（shard）到多个 Raft 复制组（shardgrp）上，从而让吞吐量随组数线性增长。 难点在于：分片会移动（有的组负载重、有的组要下线维护），而移动过程中必须保证 KV 操作仍然线性一致， 还要能从"控制器崩溃/被分区"中恢复。

必备原理
  • 配置（Configuration）：一张"分片号 → 组号"的映射表，每个配置有唯一编号 Num。存在 Lab 2 的 kvsrv 里。
  • 控制器（Controller）：管理员用它来增删 shardgrp、调整分片归属。ChangeConfigTo 负责执行一次配置变更。
  • 分片迁移三步曲：FreezeShard（冻结源组，拒绝该分片的写）→ InstallShard（把数据复制到目标组）→ DeleteShard（删除源组的冻结分片），最后发布新配置。好处是组与组之间不需要直接通信。
  • 版本栅栏（Fencing）：网络会乱序，旧 RPC 可能迟到。每个 Freeze/Install/Delete RPC 都带 Num，shardgrp 记住见过的最大 Num，拒绝过期的 RPC。
  • ErrWrongGroup：如果 shardgrp 收到不属于自己分片的请求，返回该错误；客户端重新读配置并重试。
  • 并发控制器：用 kvsrv 的版本化 Put 保证"只有一个控制器能提交下一个配置"。

Lab 说明明确指出，这个分片 KV 的设计与 Flat Datacenter Storage、BigTable、Spanner、FAWN、Apache HBase、Rosebud、Spinnaker 等一系列系统"遵循相同的总体设计"。建议对照阅读：

  • Spanner：分片 + Paxos 复制 + 配置管理，是 Lab 5 的"豪华版"。
  • GFS：同样用"中心 Master 管元数据 + 分块数据"的分层结构。
  • Chain Replication：其中关于"分片在多个服务器组上如何布局以获得负载均衡与快速修复"的讨论（§5.2–5.4），对理解 Lab 5 的分片思路很有帮助。
  • ZooKeeper：现实中常用 ZK 来存配置、做选主，与 Lab 5 用 kvsrv 存配置异曲同工。
分部分要点

实现 shardgrp、配置的读写（存在 kvsrv 里）、以及 Freeze/Install/Delete。 要点：用 shardcfg.Key2Shard() 算键的分片号；第一个组 Gid1 初始化时拥有所有分片； 迁移时要支持"不影响其他分片继续服务"。注意：如果 RPC 回复里包含服务器状态的 map，必须拷贝一份再返回，否则会和并发的修改产生竞态。

控制器是"短命命令"：它执行完就退出，但可能在执行中崩溃/被分区。 解法是同时保存"当前配置"和"下一个配置"：开始变更时先写"下一个配置"，全部完成后才把它提升为"当前配置"。 InitController 启动时先检查是否存在"编号更高的下一个配置"，有就把它执行完。 新控制器可能重复发送 Freeze/Install/Delete，靠 Num 栅栏让 shardgrp 忽略重复。

当多个控制器并发运行时（旧的可能还活着），要保证只有一个能提交下一个配置。 由于 shardgrp 的 RPC 已被 Num 栅栏保护，剩下的挑战就是"配置写入的原子性"——用 kvsrv 的版本号 + 版本化 Put， 让只有一个控制器写入成功，其他的直接返回。另外要保证新控制器执行恢复时，旧控制器不会干扰它。

开放题。可选方向：把控制器改用 kvraft（而非 kvsrv）存储配置；给 kvsrv 增加 Range 操作（用 B 树等支持范围查询的结构）； 给 kvraft 加"领导者租约"以支持不经过日志的快速读；给 kvraft 或 shardkv 增加事务（后者需要两阶段提交 + 两阶段锁）。 需要自己写测试并提交 extension.md。

  • 提交前务必重跑 make raft1、make kvraft1、make shardkv，确认前面的改动没有破坏旧测试。

调试与心态：Lab 真正的难点

课程自己的警告是"调试这些 Lab 可能非常耗时"。难的不是算法本身，而是并发 bug 的定位。下面是一些被反复验证有效的做法。

🧪 永远开 -race

评分时不带，但你自己必须带。go test -race 能抓到"结果正确但存在竞态"的代码，这类 bug 会在压力测试下随机爆发。

🔁 重复跑测试

并发 bug 是概率性的。Lab 3 说明明确建议"提交前多跑几遍测试"。跑 10 遍通过才算真的通过。

📝 打日志，但要有策略

用 log.Printf 输出关键事件（任期变化、日志追加、状态切换）。Lab 3 说明建议打印 Start 和 AppendEntries 处理，能画出完整时间线。

🧹 先写干净再写快

Lab 3 说明原话："为了后续 Lab，请把代码写（或重写）得干净清晰。"结构混乱的 Raft 在 Lab 4/5 会让你付出十倍代价。

⏱️ 警惕"太慢"

如果测试超时，多半是循环空转、RPC 太频繁、或日志回退太慢。用 time 命令查看实际耗时。

🧭 卡住就回论文

Lab 文档简略的地方，论文里往往有完整逻辑。Raft 的 Figure 2 值得反复读——"完整逻辑分散在图的好几个部分"。
