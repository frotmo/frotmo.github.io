›
vector<FeedMsg>

›
MATCH / MISMATCH
哈希一致 ⇒ 语义等价
关键：正确性校验与计时分离。校验走完整回放并采样 BBO；计时则把 Book 的构造、订单池预分配都放在计时区间之外， 只测量「回放循环」本身——否则会把内存分配开销算进去，得到虚高的 ns/msg。

通路 A′ · 计时对比 lob_bench

目标：在正确性确认后，测量两套实现的吞吐并计算加速比。

预热 1 轮
让 CPU 升频、cache 进入稳定态
›
time_replay<Array>
PF=8 预取，重复 5 次取中位数
›
time_replay<Naive>
PF=0，基线无法预取
›
g_sink
volatile 汇总，防止优化器消除循环
›
ns/msg · 加速比
10.13 vs 159.33 → 15.7×
为什么取中位数？ 笔记本 CPU 有频率波动与后台干扰，均值会被离群值污染。5 次排序后取中间值最稳健。 为什么用 volatile sink？ 否则编译器发现结果没人用，会把整个回放循环优化掉——这是基准测试最经典的陷阱。

零拷贝的意义：逐笔文件动辄数百 MB。传统「read 到缓冲区」需要额外一次完整内存拷贝； mmap 把文件直接映射进虚拟地址空间，内核按需分页，回放时像访问普通数组一样顺序扫描。

测试环境：Intel Core i5-13500HX · Windows · MSVC 19.44 · /O2 /GL /arch:AVX2（LTO）。 数据：1000 万条合成逐笔消息，取 5 次中位数（含预热）。

正确性：两版逐条回放同一数据，每 1024 条对 BBO 做 FNV 滚动哈希，完全一致——所有优化都是语义等价的，不是靠「少算」换来的性能。

读法提示：v1–v4 使用早期版本的合成数据（成交占比偏低、热路径更轻），与 v5 的绝对 ns/msg 不完全可比； 此处列出是为了体现「测量 → 定位瓶颈 → 改造」的优化思路递进。消融实验（预取开/关）在同一份数据上对比，结论最干净。
